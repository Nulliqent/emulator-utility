# P0.3 Spike: AWS SDK v3 bundle cost for 436 lazy clients

Issue #3 (parent #1). ADR-0006. Spike code: `console/spikes/sdk-registry/` (throwaway; `node_modules` and `dist` are git-ignored).

## Verdict: GO, with one build requirement

The build takes about 44 s (threshold: under about 3 minutes). The largest chunk is 227 KB gzipped (threshold: under 2 MB). The ADR-0006 contingency (eager top 50 plus Gateway-side long tail) is **not** needed.

Requirement: the Vite build needs a bigger Node heap. With Node's default old-space limit (about 4 GB) `vite build` died with `JavaScript heap out of memory` during the transform stage (about 40 s in). It passed with `NODE_OPTIONS=--max-old-space-size=12288`. Peak memory was not measured, so 12 GB is only a value known to work; the lowest working value was not searched for. The real Console build and CI need this recorded as a constraint.

## Setup

- Machine: macOS arm64, 24 GB RAM, Node v26.3.0, pnpm 10.34.9 (corepack is absent in Node 26, so run `npx pnpm@10`), Vite 7.3.8.
- SDK: all `@aws-sdk/client-*` pinned at 3.1171.0.
- Mapping: each crate's `sdk_id` becomes `@aws-sdk/client-<sdk_id lowercased, spaces to hyphens>`. All 436 names resolved with `npm view` at 3.1171.0, with no duplicates and **no missing clients**. The mapping is in `scripts/service-map.tsv`. Only package existence was verified, not that each package is semantically the intended service.
- Generator: `scripts/gen.mjs` writes `src/sdk-registry.gen.ts` (436 entries of `serviceId: () => import("@aws-sdk/client-x")`) and the `package.json` dependencies. The entry (`src/main.ts`) only references the registry.

## Measurements

| Metric | Result |
|---|---|
| Install (pnpm, 436 clients plus Vite) | about 33 s wall |
| `node_modules` size | 761 MB (`du -sh`); pnpm store 726 MB (hardlinked, so not additive on disk) |
| Packages in `.pnpm` | 501 |
| EC2 client unpacked | about 27 MB (ADR-0006 said about 18 MB) |
| Cold build (`rm -rf dist` first; 2 runs) | 43.7 s and 43.6 s (about 45 s wall) |
| Build with default Node heap | FAILED: out of memory |
| JS chunks emitted | 473 (436 service chunks plus shared chunks and the entry) |
| `dist` size | 23 MB on disk |
| Total JS | 22.9 MB raw, 5.98 MB gzip (`gzip -9`) |
| `index.html` | 130 B gzip; nothing loads until a service is used |

Largest chunks (gzip -9 / raw). Chunk names are all `dist-es-<hash>`, so they were identified by content:

1. 232,551 B (227 KB) / 1,062,642 B. Contains `RunInstances`, so it is EC2.
2. 106,260 B / 424,272 B
3. 104,879 B / 440,840 B (SageMaker)
4. 85,455 B / 365,482 B
5. 70,987 B / 274,041 B
6. 68,906 B / 269,254 B

EC2 is the largest, as expected, at about 11% of the 2 MB limit.

## Not measured

- Peak build memory, and the minimum heap that works.
- `vite dev` cold start and on-demand transform cost. Only the production build was run.
- Runtime cost in a browser (parse time, transfer from the Gateway) and calls to the emulator.
- Whether each package is the intended Service, or whether the SDK has every Operation the emulator models (the `sdk-missing` path).
- Build time with real Console code and plugins, other minification settings, or source maps (off here).
- Install time with a cold pnpm store or on Linux/CI.

## Follow-ups

- The real Console build must raise the Node heap (at least the tested 12 GB until a lower value is found), and CI needs matching RAM.
- Test `vite dev` behaviour (dependency pre-bundling of 436 clients) before Phase 1.
