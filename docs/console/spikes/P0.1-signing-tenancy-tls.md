# P0.1 Spike: pass-through signing, tenancy and TLS identity

Issue: #2 (parent #1). Date: 2026-11-18. Verifies "To verify in Phase 0" items 1 to 4 in `docs/console/DECISIONS.md`.
Spike code (throwaway): `console/spikes/proxy/` (`proxy.mjs` is about 25 lines, `drive.mjs` runs the calls).

## Method

- Proxy on `127.0.0.1:9300`. It forwards method, path, query and `Host` unchanged and strips `Origin`, `Referer`, `Cookie` and `Sec-Fetch-*`. It trusts only `ca.pem` and verifies the certificate identity as `127.0.0.1`. Bodies are piped both ways, never buffered.
- Driver: AWS SDK for JavaScript v3 (3.1171) in Node 26, signing with the Emulator Credentials, endpoint `http://127.0.0.1:9300`. A middleware added after signing attached `Origin`, `Referer`, `Cookie` and `Sec-Fetch-Site/Mode` to every request, imitating what a browser adds after the SDK signs.
- **No headless browser was used.** The Node SDK is the same code path for signing and serialisation, but Node does not enforce browser CORS, forbidden headers or `fetch` streaming. Browser-specific behaviour (see "Not verified") is untested.
- Target: the running Docker emulator (`https://127.0.0.1:9297`, request authentication on).
- The run was done twice: proxy on the host dialling `127.0.0.1:9297`, and proxy in a throwaway `node:20-alpine` container (`docker run --network emulator-utility_default`, no compose edit) dialling `emulator:9297`. Results were identical.

## 1. Pass-through signing, per protocol (all PASS)

| Call | Protocol | Result |
|---|---|---|
| SQS `ListQueues` | awsJson1_0 | 200 |
| Kinesis `ListStreams` | awsJson1_1 | 200 (see note) |
| Lambda `ListFunctions` | restJson1 | 200 |
| IAM `ListUsers` | awsQuery | 200 |
| EC2 `DescribeVpcs` | ec2Query | 200 |
| S3 `ListBuckets`, `CreateBucket` | restXml | 200 |

Host `127.0.0.1:9300` signed by the client verified at the emulator, which was reached as `127.0.0.1:9297` or `emulator:9297`. Pass-through signing holds for all six protocols.

Negative controls: a real key with the wrong secret returns 403 `SignatureDoesNotMatch`, and an access key the emulator does not know returns 403 `AccessDenied: Sign the request with the emulator credentials`. So the emulator really verifies signatures and the passes above are meaningful.

**Kinesis note (finding).** The Node SDK's Kinesis client defaults to an HTTP/2 handler. The emulator's TLS listener offers only `http/1.1`, so a direct call fails with TLS alert "no application protocol", and an h2c call to the plain-HTTP proxy fails with "Protocol error". This is the SDK default, not a proxy problem. With `requestHandler: new NodeHttpHandler()` it passes. Browsers use `fetch`, which is HTTP/1.1 against a plain-HTTP Gateway, so the SPA is not affected. Anything that runs the SDK in Node (Probes, a server-side invoker) must use the HTTP/1 handler.

## 2. S3 (all PASS, re-sign fallback not needed)

- `PutObject` 5 MB from a Buffer, with `requestChecksumCalculation` `WHEN_REQUIRED` and `WHEN_SUPPORTED` (CRC32): 200.
- `PutObject` 5 MB from a stream with `ContentLength`: 200.
- `GetObject` of the 5 MB object: SHA-256 matches the upload.
- Multipart: manual `CreateMultipartUpload`, 2 x `UploadPart` (5 MB), `CompleteMultipartUpload`: 200. `lib-storage` `Upload` of 12 MB (5 MB parts) followed by `HeadObject`: size matches.
- Path-style addressing (`forcePathStyle`) was used, as the Connection's `s3PathStyle: true` says.

**Does S3 need the re-sign fallback? No**, for everything the v3 SDK sends over a plain-HTTP endpoint. Caveat: over `http://` the SDK signs the real payload SHA-256 (`x-amz-content-sha256` is the digest, no `aws-chunked`, no `STREAMING-*` or `UNSIGNED-PAYLOAD-TRAILER`). The chained streaming signature that ADR-0003 worries about was therefore never put on the wire. The v3 SDK produces it only over HTTPS with a trailing checksum, which the Console never does because the Gateway is plain HTTP on loopback. A non-SDK client that sends `aws-chunked` through the Gateway is untested.

## 3. Tenancy: one shared state across access keys (PASS)

- `CreateQueue` with the Emulator Credentials, then `ListQueues` with an access key from IAM `CreateUser` and `CreateAccessKey`: the same queue is listed. State is shared, not sharded.
- STS `GetCallerIdentity`: the Emulator Credentials give `arn:aws:iam::000000000000:user/emulator`, the IAM-created key gives `arn:aws:iam::000000000000:user/<name>`. Both sit in account `000000000000`.
- A made-up key is refused (403), so only the Emulator Credentials and keys minted through IAM can sign.
- The comment in `vendor/server/src/lib.rs` about sharding tenants by access-key id does not match what the running binary does for these keys. The Console can keep signing with the Emulator Credentials and need not warn about per-key isolation.
- Not tested: whether keys with different IAM policies are enforced, since authorization was not in scope.

## 4. TLS identity (PASS, `network_mode` fallback not needed)

`ca.pem` is a single ECDSA P-256 self-signed certificate, subject `CN=rcgen self signed cert`, valid 1975 to 4096, with SAN `DNS:localhost, IP:127.0.0.1, IP:::1`. The container runs `aws-emulator -b 0.0.0.0`. `dialable_host` maps a wildcard bind to loopback, so the certificate is minted for `127.0.0.1` regardless of the bind address.

From a container on the compose network, trusting only `ca.pem`:

| Dial | Verification | Result |
|---|---|---|
| `emulator:9297` | default (name `emulator`) | `ERR_TLS_CERT_ALTNAME_INVALID` |
| `emulator:9297` | identity forced to `127.0.0.1` | 200 |
| `emulator:9297` | system roots, no `ca.pem` | `DEPTH_ZERO_SELF_SIGNED_CERT` |

So the Gateway can dial the compose service name, as long as it verifies against identity `127.0.0.1` (Node: `checkServerIdentity: (_, cert) => tls.checkServerIdentity('127.0.0.1', cert)`; TLS SNI cannot carry an IP, so `servername` must not be used for this). The `network_mode: service:emulator` fallback is unnecessary. The full drive suite passed through this topology. Chain trust is pinned to the one certificate in `ca.pem`.

## 5. Header stripping is required and works

Sending the same signed SQS call straight to the emulator with `Sec-Fetch-Site: cross-site` and an `Origin` returns 403 `AccessDenied: Requests a browser sends from another site are refused`. The identical request through the proxy returns 200, because the proxy removes those headers. `Sec-Fetch-Site: same-origin` is accepted by the emulator directly. The unsigned `Origin`/`Referer`/`Cookie`/`Sec-Fetch-*` headers did not affect signature verification.

## Recommendation for ADR-0003

Accept pass-through signing as written, with these clarifications:

1. Keep "S3 re-signs only if Phase 0 fails" as a closed branch: Phase 0 passed, so remove the fallback from the plan. Record that streaming-signed `aws-chunked` bodies were not exercised, and reopen only if the Console starts sending them (for example if the Gateway moves to HTTPS).
2. In ARCHITECTURE 3.9, say that Node-side SDK clients must use the HTTP/1.1 request handler (the emulator offers only `http/1.1` in ALPN).
3. In ARCHITECTURE 3.9, say how to pin identity: dial the service name and override the identity check to `127.0.0.1`. Drop the `network_mode` fallback.
4. Keep the Gateway's own same-origin check. The emulator's browser rule applies to whatever reaches it, so the Gateway must strip as above, and must refuse cross-site requests itself.
5. Tenancy needs no extra UI warning.

## Not verified

- No real browser: `fetch` behaviour, `Expect: 100-continue`, forbidden-header handling, CORS preflight against the Gateway and large browser uploads.
- `aws-chunked` / `STREAMING-AWS4-HMAC-SHA256-PAYLOAD` uploads (see section 2).
- Credentials rotation after an emulator restart (the container was not restarted, as instructed).
- The Smithy RPC v2 CBOR protocol and any service outside the six listed.
- Non-Node TLS stacks accepting a self-signed leaf as a trust anchor. Node did.
- Leftovers in the running emulator from the spike: a few `spike-*` buckets, queues and an IAM user with an access key.
